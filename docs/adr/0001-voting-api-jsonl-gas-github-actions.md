# ADR-0001: 民謡ABC投票APIとJSONLデータ管理

- Status: Accepted for initial prototype
- Date: 2026-10-13
- Decision owners: 民謡ABC project

## Context

「民謡ABC」では、公開候補100曲から読者投票を行い、結果を参考に書籍収録用の表の26曲を選ぶ。別枠の「秘密の26曲」は編集企画として管理し、公開投票の候補・画面・APIレスポンスには含めない。

フロントエンドはスマートフォンで使えるPWAとし、GitHub Pagesから配信する。曲データや投票記録はJSONLを扱いやすい正本形式として管理し、REST APIで読み書きできる構成を目指す。GitHub Actions（WF）は検証・集計・ランキング生成などのバッチ処理に使う。

## Decision

初期構成は次の責務分担とする。

1. **GitHub Pages**: PWAと公開用の曲データを配信する。
2. **GAS Web App**: REST APIの入口。リクエストの検証、投票受付、管理操作の制御を行う。
3. **GitHub REST API**: サーバー側からリポジトリ内JSONLを取得・更新するために利用する。
4. **JSONL**: 曲目などの低頻度更新データ、および必要に応じて確定済み投票記録・集計スナップショットを保存する。
5. **GitHub Actions**: テスト、データ検証、集計、ランキングや公開用JSONの生成を行う。Actions自体を常時稼働のHTTP APIとしては扱わない。
6. **秘密の26曲**: 公開候補・公開API・公開リポジトリから分離する。アクセス制限された編集用の保管先で管理する。

### API案

| Method | Path | 用途 | 公開範囲 |
|---|---|---|---|
| GET | `/songs` | 公開候補曲一覧を取得 | 公開 |
| GET | `/songs/{id}` | 公開候補曲の詳細を取得 | 公開 |
| POST | `/votes` | 最大5曲の投票を送信 | 公開・入力検証必須 |
| GET | `/ranking` | 集計済みランキングを取得 | 公開 |
| POST | `/admin/songs` | 曲データを追加 | 管理者限定 |
| PATCH | `/admin/songs/{id}` | 曲データを更新 | 管理者限定 |

パスとHTTPメソッドは初期案であり、実装前にGAS Web Appの制約やCORS・レスポンス仕様を検証する。

## Data and write strategy

- 曲データのような更新頻度の低いJSONLは、GASからGitHub REST API経由で更新できる。
- GitHub Contents APIでファイルを更新する際は、基本的にファイル全体を取得・更新し、現在のblob SHAを使ってコミットする。
- **投票のたびに共有JSONLを読み書きする方式は採用しない。** 同時更新によるSHA競合、全ファイル書き換え、実行時間・API制限のリスクがあるため。
- 投票受付は重複送信を識別できる記録とともに受け付け、集計・JSONL反映はバッチ化する。試作段階ではGAS側の一時保存先を使い、投票件数や同時実行の実測後に保存先を再評価する。
- 集計結果は生成物として公開し、公開ランキングと個人の投票記録を分ける。

## Security and integrity

- GitHub書き込みトークンをPWAやブラウザーへ絶対に渡さない。サーバー側の設定に保管し、必要最小限の権限にする。
- 投票APIは曲IDの許可リスト、選択数（最大5曲）、入力形式、サイズ、レート制限を検証する。
- 匿名投票では、端末内保存やIP制限だけで「1人1票」を保証できない。投票ルールは「期間中の再投票を許すか」「重複をどう扱うか」を別途明文化する。
- GASの公開Web Appは認証・CORS・クォータ・同時実行制限を実環境で検証する。
- 公開用データに秘密の26曲や非公開の編集メモを混入させない。

## Alternatives considered

- **GitHub Pagesだけ**: 配信とオフライン表示には適するが、共有投票の受付・集計はできない。
- **GitHub ActionsをAPI入口にする**: ActionsはHTTPリクエストを常時直接受けるAPIサーバーではないため、入口として採用しない。
- **Cloudflare Workers + D1**: 公開APIと高頻度の投票書き込みに向く候補。まずは構成を軽くするため初期案では保留し、負荷やクォータが要件を超えたら再検討する。
- **GAS + Google Sheetsを正本にする**: 実装が簡単だが、JSONLを正本としてGit管理したいという希望とは異なるため、初期の正本にはしない。

## Consequences

### Benefits
- PWA、API、データ、バッチ処理の責務を分離できる。
- 曲データと設計の変更履歴をGitで追跡できる。
- Cloudflareなどの追加サービスを、必要性が明らかになってから導入できる。

### Costs and limitations
- GASからGitHub REST APIを使うための認証管理とエラー処理が必要。
- JSONLをGitHubに保存する方式は、高頻度・高並行の投票書き込みに適さない。
- 匿名投票の厳密な一人一票は保証できず、必要なら認証や別の保存基盤が必要。
- 実運用開始前に、API契約、投票期間、再投票ルール、データ保持方針、クォータと負荷を検証する必要がある。

## Acceptance criteria

- [ ] 公開候補100曲と秘密の26曲がデータ・配信経路ともに分離されている。
- [ ] PWAから公開曲一覧を取得できる。
- [ ] 投票APIが最大5曲の入力検証を行う。
- [ ] 書き込みトークンがクライアントへ露出しない。
- [ ] 同時送信・再送・GitHub API失敗時の挙動をテストする。
- [ ] ランキングは投票記録から再生成でき、手作業の値を正本にしない。
- [ ] 公開前にGASのCORS、認証、クォータ、デプロイ設定を実機検証する。
