# ADR-0001: 民謡ABC投票API・LINEミニアプリ認証・JSONLデータ管理

- Status: Accepted for initial prototype
- Date: 2026-10-13
- Decision owners: 民謡ABC project

## Context

「民謡ABC」では、公開候補100曲から読者投票を行い、結果を参考に書籍収録用の表の26曲を選ぶ。別枠の「秘密の26曲」は編集企画として管理し、公開投票の候補・画面・APIレスポンスには含めない。

フロントエンドはLINEミニアプリとし、LINE上で利用者認証を行ってから投票画面を利用できるようにする。投票APIと保存先にはCloudflareを採用し、JSONLはGitHubで管理・追跡できるデータ形式として活用する。GitHub Actions（WF）は検証・集計・ランキング生成・JSONL出力などのバッチ処理を担当する。

## Decision

初期構成は次の責務分担とする。

1. **LINEミニアプリ**: 投票UI、曲の検索・選択、認証フローの開始。
2. **LINE認証**: ミニアプリから得たIDトークン等をサーバーへ送信し、サーバー側でLINEの検証手順を用いて検証する。クライアントでデコードしたプロフィール情報だけを本人確認として信用しない。
3. **Cloudflare Workers**: REST APIの入口。認証済み利用者の識別、入力検証、投票受付、レート制限、管理APIの制御を行う。
4. **Cloudflare D1**: 投票記録の運用上の正本。投票の書き込みと集計に利用する。LINEのユーザー識別子は必要最小限で保持し、公開ランキングには含めない。
5. **GitHub Actions**: 定期または手動でデータ検証、集計、ランキング生成、JSONLへのエクスポートを行う。Actions自体を常時稼働のHTTP APIとしては扱わない。
6. **GitHub / JSONL**: 曲データ、スキーマ、設計文書、生成された投票集計スナップショットをバージョン管理する。高頻度の投票をリポジトリのJSONLへ直接追記しない。
7. **秘密の26曲**: 公開候補・公開API・公開リポジトリから分離し、アクセス制限された編集用保管先で管理する。

## Request flow

1. 利用者がLINEミニアプリを開き、LINEの認証フローを通る。
2. クライアントはLINEから取得したIDトークン等をWorkers APIへ送る。
3. Workers側でLINEの公式検証手順を実行し、発行元・対象チャンネル・有効期限等を確認する。未検証のユーザーIDやクライアント申告値だけでは投票を受け付けない。
4. 認証済み利用者の識別子を使って投票ルールを適用し、曲IDの許可リストと最大5曲の選択数を検証する。
5. 投票記録をD1に保存する。
6. 集計処理でランキングを生成し、必要な公開データをJSONL等に出力してGitHubへ反映する。

## API proposal

| Method | Path | Purpose | Access |
|---|---|---|---|
| GET | `/api/songs` | 公開候補曲一覧を取得 | 公開 |
| GET | `/api/songs/{id}` | 公開候補曲の詳細を取得 | 公開 |
| POST | `/api/votes` | 最大5曲の投票を送信 | LINE認証必須 |
| GET | `/api/ranking` | 集計済みランキングを取得 | 公開 |
| POST | `/api/admin/songs` | 曲データを追加 | 管理者限定 |
| PATCH | `/api/admin/songs/{id}` | 曲データを更新 | 管理者限定 |

パスとレスポンス形式は初期案であり、実装時に確定する。

## Vote rules and integrity

- LINE認証は利用者を識別するための基盤とする。ただし、同一人物が複数のLINEアカウントを持つ可能性はあり、LINE認証だけで現実の一人一票を完全に保証するものではない。
- 投票ルールとして、期間中の再投票を許すか、再投票時に前回投票を置き換えるか、投票後に変更できるかを実装前に確定する。
- 同一リクエストの再送で票が二重登録されないよう、冪等性キーまたは同等の重複処理を設計する。
- Workers側で曲IDの許可リスト、選択数（最大5曲）、入力形式・サイズ、レート制限を検証する。
- LINEトークンやチャンネル秘密情報をブラウザーへ埋め込まない。必要な秘密情報はサーバー側の環境設定に保存する。
- 公開ランキングと個人の投票記録を分離し、公開レスポンスに個人識別子を含めない。
- 公開用データに秘密の26曲や非公開の編集メモを混入させない。

## Data strategy

- D1は頻繁に更新される投票記録の運用上の正本とする。
- GitHubのJSONLは、曲データの管理、エクスポート、監査可能なスナップショット、再利用可能な出版データに利用する。
- GitHub Contents APIでファイルを更新する場合は、ファイル全体の取得・更新とblob SHAの管理が必要で、同時更新が競合しうる。したがって投票リクエストごとにJSONLを書き換えない。
- GitHub ActionsはD1から安全にデータを取得できる仕組み、またはWorkersからエクスポートデータを受け取る仕組みを別途設けて、JSONLを生成・検証する。認証情報はGitHub Actions Secrets等で保護する。
- JSONLの出力スキーマ、個人識別子を含めるか、保持期間、公開範囲は実装前に定める。公開JSONLには集計結果を優先し、生の投票履歴やLINEユーザーIDを含めない。

## Alternatives considered

- **GAS + GitHub REST API**: 小規模な試作には使えるが、今回の認証付き投票APIとD1中心の構成では採用しない。
- **Firebase Authentication + Firestore**: 認証とデータ保存を統合しやすい代替案。今回はLINEミニアプリを認証導線とし、REST APIとJSONL/GitHub連携を明示的に制御したいため、初期案では採用しない。
- **GitHub Pagesだけ**: 静的配信には適するが、認証付き投票受付と共有データ保存には不十分。
- **GitHub ActionsをAPI入口にする**: Actionsは常時稼働のHTTP APIではないため採用しない。
- **GitHub JSONLを投票の直接保存先にする**: 高頻度書き込みと同時更新に適さないため採用しない。

## Consequences

### Benefits
- LINE上から参加しやすい投票導線を作れる。
- サーバー側で認証検証と投票ルールを一元化できる。
- D1で投票を書き込み、GitHub Actionsで集計・JSONL化することで、運用処理と出版データを分離できる。
- GitHubでスキーマ、設計、集計スナップショットの変更履歴を追跡できる。

### Costs and limitations
- LINEミニアプリのチャネル設定・審査・権限設定と、サーバー側トークン検証の実装が必要。
- D1スキーマ、投票更新ルール、集計処理、JSONLエクスポートを実装する必要がある。
- LINEアカウント単位の識別は、実在する一人の厳密な本人性を保証しない。
- GitHub ActionsからD1データを取得・出力するための安全な連携方式を決める必要がある。

## Acceptance criteria

- [ ] LINEミニアプリから投票画面を開ける。
- [ ] WorkersがLINEの認証情報をサーバー側で検証し、未検証リクエストを拒否する。
- [ ] 認証済み利用者のみ投票を送信できる。
- [ ] 投票APIが最大5曲の入力検証を行う。
- [ ] 再送による二重投票の挙動が定義・テストされている。
- [ ] D1に投票を記録し、集計結果を生成できる。
- [ ] GitHub Actionsで集計・検証済みJSONLを出力できる。
- [ ] GitHub/LINEの秘密情報や個人識別子が公開データへ漏れない。
- [ ] 公開候補100曲と秘密の26曲がデータ・配信経路ともに分離されている。
- [ ] LINEミニアプリの権限、認証、Workers APIのレート制限、エラー処理を実機検証する。
